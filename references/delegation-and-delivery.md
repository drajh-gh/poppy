# Delegation and delivery

## Composition first

Poppy composes available Codex-native and project-specific skills. It does not duplicate their domain instructions. Inspect the skills available in the current task and load only those that materially improve the work.

For software delivery, consider product intent, user experience, architecture, implementation, testing, security, observability, release, and operations. Use only the perspectives that could change the outcome.

## Delegation economics

Continue in the informed task by default. Delegate only when a bounded independent result can proceed without steering and its expected decision value, coverage, or independence exceeds the context-transfer and integration cost. Project instructions and the user's current request govern whether delegation is available. Fresh read-only assurance at a material gate is a deliberate use; routine implementation, same-candidate corrections, and shared-context follow-ups normally stay with the informed owner.

- Keep one writer per target.
- A delegated writer receives its own isolated worktree and an explicit file boundary.
- Delegates without a writer assignment remain read-only.
- The root retains authority, integrates results, resolves conflicts, and verifies the final candidate.
- Do not let two workers run CPU-intensive local checks concurrently.

## Delivery shape

For a rough idea or defect:

1. establish the desired outcome and current evidence;
2. surface the smallest decision that unlocks progress;
3. recommend a solution with material tradeoffs;
4. implement within the authorized target;
5. verify the changed behavior; and
6. report what changed, what passed, and what remains unverified or conflicted.

Use an ephemeral native plan only when dependencies or joins matter. Do not create a manifest, persistent ledger, run receipt, or generalized graph.

## Phase boundaries and context

At a natural phase boundary, decide in this order:

1. Continue when the next phase needs the current reasoning or evidence verbatim and still fits safely.
2. Start fresh when prior context is irrelevant and the next input is self-contained.
3. Create a portable handoff only when work must travel to another harness, repository or worktree, person, or separately owned task.
4. Delegate when a bounded independent task can run without steering and the root context should remain intact.
5. Otherwise compact for an explicitly named next phase, retaining the objective, decisions, evidence and provenance, constraints, acceptance conditions, authority, and unresolved or conflicted claims.

Do not clear or compact mid-phase merely for tidiness. Continue or split a bounded remainder. Context transitions are informational only and never expand authority. Handoffs and compactions are lossy secondary sources, so retain links to primary evidence and preserve reasoning that the next phase still needs.
