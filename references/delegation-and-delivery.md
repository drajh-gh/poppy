# Delegation and delivery

## Composition first

Poppy composes available Codex-native and project-specific skills. It does not duplicate their domain instructions. Inspect the skills available in the current task and load only those that materially improve the work.

For software delivery, consider product intent, user experience, architecture, implementation, testing, security, observability, release, and operations. Use only the perspectives that could change the outcome.

## Personal delegation preference

The owner of this personal installation prefers adaptive sub-agent use whenever it is useful. Delegate bounded, independent lanes that improve speed, coverage, or independence; do not delegate merely to create ceremony.

- Keep one writer per target.
- A delegated writer receives its own isolated worktree and an explicit file boundary.
- Delegates without a writer assignment remain read-only.
- The root retains authority, integrates results, resolves conflicts, and verifies the final candidate.
- Do not let two workers run CPU-intensive local checks concurrently.

## Delivery shape

For a rough idea or defect:

1. establish the desired outcome and current evidence;
2. surface the smallest decision that unlocks progress;
3. recommend a solution with material tradeoffs;
4. implement within the authorized target;
5. verify the changed behavior; and
6. report what changed, what passed, and what remains Gray.

Use an ephemeral native plan only when dependencies or joins matter. Do not create a manifest, persistent ledger, run receipt, or generalized graph.
