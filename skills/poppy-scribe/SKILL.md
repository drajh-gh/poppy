# Poppy Scribe

Keep task meaning and operational learning recoverable without creating a transcript, hidden state, shadow tracker, or second source of truth.

Read [Scribe checkpoints and artifacts](../../references/scribe-checkpoints.md) before creating, reviewing, forgetting, persisting, or comparing Scribe state or records.

## Own semantic reconstruction, not truth

Represent only material state: current intent, decisions with status, evidence limits, candidate changes, open questions, one next step, and at most one attention flag. Reconcile earlier summaries and records against the newest user intent and closest primary evidence before relying on them.

A checkpoint or Scribe artifact never establishes project facts, completion, acceptance, tracker state, canonical memory, authority, or the success of an external effect. Substantive owners decide those states; Housekeeping owns Codex lifecycle metadata; Context resolves project identity, source authority, and valid vault destinations; Learn governs durable lessons.

## Choose the smallest mode

- **Quiet:** maintain the latest checkpoint in current conversation context and surface at most one material conflict, drift, stale-evidence risk, blind retry, or unsupported closure.
- **Review:** answer an explicit checkpoint, handoff, “what changed,” evidence-limit, or challenge request from the latest context plus current evidence.
- **Incident:** after the failure is corrected or contained, prepare one semantic operational incident. Keep it in conversation unless the user also approves an exact configured project-vault file effect.
- **Improve:** analyze a bounded set of explicitly supplied summaries or explicitly selected configured Scribe records. Claim recurrence only when the same supported fingerprint spans at least three independent task identities. A direct user decision or safety requirement may justify a non-recurring intervention when labelled as such.

Do not infer activation from ordinary substantive work or from the word “Scribe.” Activate only when the user explicitly asks, affirmatively accepts Root Poppy's current offer, or has supplied an applicable standing preference. Root may recommend Scribe before continuity-risk work or after correcting a material Poppy or Codex mistake, but the recommendation itself does not activate it. Keep Scribe active within the current task until the user asks it to stop or forget.

## Keep checkpoints conversation-bound

Maintain a checkpoint in current conversation context only. Do not append raw JSON, HTML comments, hidden markers, or machine-readable control payloads to an assistant response. Current Codex hooks do not provide a verified private model-to-hook checkpoint channel, so never claim automatic checkpoint persistence, restoration, expiry, deletion, or cross-task hydration.

If an earlier summary conflicts with current evidence or user intent, preserve the conflict explicitly instead of smoothing it away. When the user asks Scribe to stop or forget, stop maintaining the conversation checkpoint. This does not delete conversation history, project artifacts, tracker state, canonical memory, or visible incident files.

## Gate visible incident artifacts

An incident file is an explicit local artifact effect, not checkpoint transport or canonical memory.

1. Confirm that the user requested a visible incident record and that the problem is corrected or contained.
2. Use Poppy Context to resolve one exact project and read only its applicable vault instructions and required Scribe configuration.
3. Validate the configured incident root stays inside the nominated vault and outside human-owned paths. Never invent a vault, fall back to the repository, or scan sibling projects.
4. Prepare one semantic record containing the expected behaviour, observed failure, material consequence, correction or current state, evidence pointer and status, follow-through, stable fingerprint, and redactions.
5. Show the exact target, material content, risk, read-back, and rollback. Obtain approval after that preview; an earlier general request is not approval of an unseen target.
6. Write only the approved record, preserve any existing file, and read the exact destination back before reporting success.

Never store raw prompts, transcript excerpts, credentials, access instructions, raw production rows, unnecessary personal data, broad project records, or every failed attempt. Full non-Poppy evidence stays in the nominated project vault. A separately approved aggregation signal preserves transferable semantics and opaque source identity while omitting unnecessary project detail.

## Analyze improvements without automatic remediation

For Improve, name the exact supplied summaries or configured record root, review window, maximum records, and stopping condition before inspection. Deduplicate source incidents and same-task repeats. Report the fingerprint, bounded examples, evidence limits, consequence, smallest intervention, and counterexample or expiry condition.

Treat every improvement as proposed unless the user separately selects and authorizes implementation. Scribe never changes policy, skills, memory, trackers, repositories, automations, installations, publications, or deployments by itself. Only a later completed supported outcome may be considered by Poppy Learn.

Lead reviews, incidents, and improvement answers with the usable finding. Keep routine checkpoint mechanics invisible.
