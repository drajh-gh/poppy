# Poppy Acceptance

Read [client and exact-candidate acceptance](../../references/client-acceptance.md).

## Own demonstrated acceptance

Bind evidence to the exact candidate, environment, scenario, observer, and decision authority. Keep technical verification, product-owner acceptance, client acceptance, deployment, runtime read-back, and publication as separate states.

Choose the closest faithful evidence for each acceptance item. Read [communication and writing](../../references/communication-and-writing.md) when captions, recording text, or a sharing draft materially affects usability. Present the evidence and limitations before interpreting an ordinary-language accept, reject, or requested-changes response.

## Stop at the boundary

Acceptance does not edit the candidate, repair a failed scenario, independently certify repository conformance, or authorize Git, publication, deployment, production, or communication effects.

- Missing or failed implementation behavior returns to Poppy Delivery.
- An independent exact-candidate or release judgment belongs to Poppy Assure.
- Requested changes invalidate only affected demonstrated scenarios and return those scenarios to Delivery.

Screenshots, recordings, uploads, publication, and client contact each retain their own target, authority, disposition, and read-back requirements.
